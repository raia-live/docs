# Multi-Tenant Foundation

Every request to SenseLab is authenticated, authorised, scoped, and metered.
This page describes how that works on SenseLab Cloud.

## Account Isolation

SenseLab Security enforces hard isolation between accounts at the storage layer,
below the application. One account cannot see another's data, even in the event
of a bug in application code — the isolation does not depend on the application
remembering to filter.

## Roles

A member of an account holds one role, which decides what they can do:

| Role | Can do |
|:-----|:-------|
| **Admin** | Everything: account and member management, API keys, all memory operations, and the Security area |
| **Developer** | Read and write memory, manage API keys, view audit logs |
| **User** | Read memory within the paths they are scoped to |
| **Security** | The Security area only — findings, rules, and policy |

Rooms and teams have their own lighter-weight roles for collaborators and
viewers, covered in [Room Members and Permissions](/amfs/concepts/room-members).

## Scoped API Keys

Each agent or tool gets its own key, and a key can be restricted to part of your
memory rather than all of it:

```
checkout-service/**   read_write
shared/patterns/*     read
```

Patterns support `*` for a single level and `**` to match everything beneath a
path. Permissions are `read`, `write`, or `read_write`. An agent can only reach
memory inside its scope — this is **permissioned inference**, enforced by the
server on every request rather than by convention.

Keys are issued from **Settings → API Keys** in the dashboard and are shown once
at creation. Store the key when you create it; only its prefix is retained
afterwards, so a lost key must be revoked and reissued.

## How Agents Connect

All external access — MCP clients, SDKs, and direct REST calls — goes through
the SenseLab HTTP API with an API key. The API resolves which account the key
belongs to, enforces the key's entity-path scopes, applies the account's rate
limit, meters the operation, and logs it. Agents never talk to the database.

## Rate Limiting

Requests are limited per key using a sliding 60-second window. Every response
carries the current state so a client can back off before it is refused:

| Header | Meaning |
|:-------|:--------|
| `X-RateLimit-Limit` | Requests allowed in the window |
| `X-RateLimit-Remaining` | Requests still available |
| `X-RateLimit-Window` | Window length in seconds |

A refused request returns 429 with `Retry-After`. Admin keys bypass the limit.

## Audit Logging

Sensitive operations — memory writes, API key creation and revocation, and
account administration — are recorded to an append-only audit log with the
actor, the action, the resource, and a timestamp. Browse it under
**Settings → Audit**.

## Usage & Quotas

Each plan includes a monthly allowance of operations plus limits on seats, API
keys, open rooms, and room guests. Usage is metered as it happens and visible
under **Settings → Usage**. See [Billing & Metering](/amfs/pro/billing) for what
counts as an operation and what each plan includes.
