SenseLab records what an agent learns as a [timeline](/amfs/concepts/git-timeline)
of events on `main`. Branching adds the rest of the Git model on top: learning an
agent does on a branch, review before it lands, a tag on a known-good state, and
rollback to it when something goes wrong.

<Note>
Branching is available on Pro, Teams, and Enterprise. You will find it under the
**Git Repository** section of any agent's page in the dashboard;
[Learning as Git](/amfs/guides/learning-as-git) walks through that section tab
by tab.
</Note>

## Branches

Create a branch from an agent's `main` learning and let the agent write to it
without touching what everyone else reads. Diff the branch against `main` to see
exactly what changed, then merge it or throw it away.

This is what makes risky work safe. An agent trying a new approach can build up
a whole set of beliefs on a branch, and if the approach turns out to be wrong,
none of it ever reaches the learning other agents rely on. It is also how
SenseLab itself works: a [fix](/amfs/guides/behavior#fixes) is drafted and
tested on its own branch and only merged into `main` when it ships.

Merges default to fast-forward. Where the same entry changed on both sides, the
merge reports the conflict and you choose which version wins — per entry, or
for the whole merge with *Branch Wins* or *Main Wins*.

## Pull Requests

A branch can be opened as a pull request so a person or another agent reviews
what was learned before it lands on `main`. Reviews come in three kinds:

| Review | Meaning |
|:-------|:--------|
| **Approved** | The reviewer is happy for this to merge |
| **Changes requested** | Something needs fixing first |
| **Commented** | Feedback without a verdict either way |

<Note>
The dashboard lists pull requests and their reviews, and lets you create, merge,
and close them. Submitting a review is done by agents through the API.
</Note>

## Branch Access Control

Grant read or read/write access to a branch, so a branch of sensitive or
in-progress learning is not readable by every agent on the account. Grants are
made to an API key or a team, and each grant is either `read` or `read_write`.

Access is enforced by SenseLab on API-key traffic to the entry and search
endpoints: a request targeting a non-`main` branch is checked against that
branch's grants and refused with a 403 if it does not have them. Writes require
`read_write` — a `read` grant can see the branch but not change it.

## Tags & Rollback

Tag a point on the timeline with a name, then roll the agent's learning back to
either a tag or a specific moment. This is the recovery path when an agent
learns something wrong and acts on it repeatedly: instead of hunting down each
bad entry, return what the agent knows to a state you know was good. Nothing is
deleted by a rollback — the superseded versions stay in the history — but there
is no undo, so tag the current state first.

## Cherry-pick & Fork

**Cherry-pick** moves selected entries between branches when you want one useful
thing from a branch you are otherwise discarding. It is available through the
API.

**Fork** copies everything an agent has learned to a new agent — the fast way to
stand up a second agent that should start out knowing everything the first one
does.

## Sacred Timeline

The default view in the Git Repository section is an interactive 3D
visualisation of how the agent's learning evolved: event nodes along the
timeline, forks where branches split off, and a detail panel for any event you
click. Next to it, **Event Log** shows the same history as a chronological list,
which is usually the faster way to find a specific entry.
