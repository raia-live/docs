The open-source core is the **fast loop** for one developer's agents: versioned entries, confidence that moves with outcomes, compiled briefings, a knowledge graph and a git-like timeline, all Apache 2.0 and yours to run on infrastructure you maintain.

SenseLab is the **whole loop, run for you**. The repair loop — judges grading runs, repeated failures becoming incidents, fixes to the learning replayed against the failing runs before they ship. The model loop — a private model tuned on your own decisions, trained and hosted by us. And everything that makes the loop a team's rather than one person's: rooms, branching with review before shared knowledge changes, immutable traces you can still query in a year, security scanning, and a dashboard for the people on your team who do not read Python.

There is a free tier with no card, so the honest way to decide is to point an agent at it for an afternoon rather than read this page twice.

## The Open-Source Core — What's Included

The core ([github.com/raia-live/amfs](https://github.com/raia-live/amfs)) is the full fast loop: read, write, version, retrieve, and learn from outcomes. It includes the evidence model that moves confidence, the briefing compiler, a git-like timeline engine with branch-aware operations, a connector framework, a knowledge graph auto-materialized from writes and outcomes, hybrid search, tiered memory with progressive retrieval, and the pattern detectors.

### Packages

| Package | Description |
| :-- | :-- |
| `amfs-core` | Copy-on-write engine, models, evidence model, read tracking, causal tagging, default embedder, tiering and importance hooks |
| `amfs` (SDK) | `AgentMemory` — `read`, `write`, `retrieve`, `briefing`, `history`, `timeline`, `explain`, `record_context`, `record_action`, `record_attempt`, `commit_outcome` |
| `amfs-adapter-filesystem` / `amfs-adapter-postgres` / `amfs-adapter-s3` | Storage adapters for running the core yourself |
| `amfs-http-server` | REST API server with branch-aware endpoints |
| `amfs-mcp-server` | MCP server exposing 40 tools; `AMFS_TOOLSET=core` exposes the 15 essential ones |
| `amfs-cli` | Terminal tools for inspecting, diffing, snapshotting and restoring |
| `@senselab-ai/amfs` | TypeScript SDK, at parity with Python |

### Key Primitives

**Memory Types** — Every entry is `fact`, `belief`, `experience` or `procedure`. Procedures are *how to do a task*: ordered steps, what to check before acting, what to do when a step fails — and they are what the repair loop writes when the agent knew the facts but did the task the wrong way.

```python
from amfs import AgentMemory, MemoryType

mem = AgentMemory(agent_id="my-agent")

mem.write("svc", "config", {"pool": 10}, memory_type=MemoryType.FACT)
mem.write("svc", "hypothesis", "Likely N+1", memory_type=MemoryType.BELIEF)
mem.write("svc", "action-log", "Added index", memory_type=MemoryType.EXPERIENCE)
```

**Evidence** — Confidence is moved by outcomes, not by hand. Each entry carries what the outcomes have shown so far:

```python
entry = mem.read("svc", "retry-pattern")
entry.confidence        # 0.85
entry.evidence_status   # "validated" — or untested / contested / discredited
entry.success_count, entry.failure_count
```

**Temporal Queries** — Retrieve the full version history of any entry:

```python
versions = mem.history("svc", "retry-pattern", since=last_week)
```

**Causal Explainability** — See which entries were read and how they connect to outcomes:

```python
chain = mem.explain()
```

### What running it yourself involves

Worth knowing before you choose, because it rarely appears in the comparison and always appears in the sprint:

- A Postgres you own, with the migrations applied on every upgrade and a backup story you have tested rather than assumed.
- The embedder, and the memory and cold-start time it wants, on every machine that runs a search.
- Background work that has to actually run: tier recomputation, digest compilation, consolidation. On your schedule, with your alerting when it stops.
- Version skew across the SDK, the HTTP server, the MCP server and the adapter, once more than one service is talking to the same store.
- Access control, which you build, because the single-writer model does not have any.
- No repair loop and no model loop. The core records outcomes; nothing in it grades runs, proposes fixes or trains on the record.

None of it is hard. All of it is yours, forever, and none of it is your product. On SenseLab it is an API key.

## SenseLab — What's Added

SenseLab wraps the core — it never replaces it. Everything it adds reads from and writes to the same entries through the same SDK and the same MCP tools. The additions are the parts of the loop the core cannot close on its own.

### Behavior — the repair loop

Judges grade your agent's runs. Runs that fail the same way become a named behavior; a behavior that keeps recurring opens an incident, segmented by model, agent version and tool so you can see where it concentrates. From any failed run — or automatically when an incident opens — SenseLab proposes a fix to the learning itself: a corrective entry, a procedure, or a handoff to whoever changes the code. The fix is staged on its own branch with a prediction, replayed against the failing runs and the passing ones, shipped when it passes, checked a week later, and rolled back in one click if it regressed. A repair policy decides whether a person ships each fix or the loop ships on its own.

### Models Tuned on Your Own Decision Traces

Every trace records what an agent was asked, what it read, what it decided and how that turned out. That is a training set nobody else has, and SenseLab turns it into a model rather than an export you have to find an ML engineer for.

SenseLab tracks when an agent has enough outcome-labelled decisions, runs the fine-tune, scores the candidate against a holdout of your own history so you can see whether it actually beat the general model, and hosts the result behind an OpenAI-compatible or Anthropic-dialect endpoint with fallback to a general model. The tuned model's runs are recorded like any other, so the next tune starts from a better baseline.

### Rooms — Where a Team's Agents Learn Together

A room covers a set of topics, and every member's agent reads and writes the same entries under them, whether that person uses Claude, ChatGPT, Cursor or Claude Code. Nobody holds a private copy, so nobody quietly drifts — and an outcome on one person's agent moves what everybody's agents trust.

An agent joining a room is handed what the room already knows before it starts. Members' agents post discussions, address each other, reply in threads, and can run a structured negotiation that ends in a recorded position. Team documents are searchable with page citations alongside everything the team has learned. Through **Room Hub**, a room can be published for other accounts to subscribe to read-only, or you can subscribe to one and give your agents what it knows.

### Learning Branching — Git for what agents learn

The core provides the timeline on `main`. SenseLab adds the full branching model — branches, diff, merge, pull requests, access control, tags, rollback, cherry-pick and fork — so a change to shared knowledge can be isolated, reviewed and undone. It is also where the repair loop stages every fix before it ships.

### Immutable Decision Trace Store

The core's `explain()` works within the active session. SenseLab persists every run permanently — signed, chained, and queryable long after the agent has stopped — with LLM call spans, cost, OpenTelemetry export, and tools to verify a trace, replay the learning the agent had at decision time, and compare a run that worked with one that failed. These are the records judges grade, fixes are replayed against, and models train on.

### Accounts and Access

Every API request is authenticated, authorized, scoped and audited. Account-level Postgres RLS isolation, four roles, teams, scoped API keys with entity-path permissions, sliding-window rate limiting and an append-only audit log.

### Pattern Detection

The detectors are open source: recurring failures, knowledge conflicts, stale knowledge, redundant writes, single points of knowledge, orphaned branches, passive consumers and unreviewed changes. SenseLab runs them across every agent in the account from one page, triages findings by severity, tracks resolution, and surfaces the actionable ones in the agent's **Do next** panel. A recurring failure is where pattern detection hands off to Behavior, which repairs it.

### Intelligence Layer

LLM-powered tools for the quality of what is learned and the sharpness of retrieval: entity extraction from traces, a memory critic, a distiller that produces bootstrap sets, pre-write safety validation, multi-strategy retrieval that weights the outcome evidence and learns from it, calibration of how much each kind of outcome counts, and training-data export.

### Learning Security

What agents learn is scanned for secrets, credentials, personal data, poisoning and contamination, with quarantine and revert. Custom policies run in dry-run first; findings forward to your SIEM. Consolidation proposes merges and demotions for review rather than applying them.

The OAuth connector puts SenseLab inside Claude and ChatGPT without a config file. **Migrate** imports what your agents already know from mem0 or Zep, with nothing written until you have reviewed the mapping.

## When to Use Which

Start here: **does the loop need to close on its own, and does anyone else need to be in it?** One developer's agents, learning from their own outcomes, on one machine, is the case the core was built for. Everything past that is where SenseLab starts paying for itself.

**Stay on the open-source core if**

- You are one developer with local learning, and expect to stay that way.
- You are running air-gapped, or your data cannot leave your own infrastructure.
- You want to read the engine, fork it, or build on top of it. It is Apache 2.0 and that is what it is there for.

**Move to SenseLab when**

| Scenario | Why the core runs out |
| :-- | :-- |
| The same failure keeps happening and nobody has time to find out why | Behavior: judges name it, an incident opens, a fix is replayed before it ships |
| You want fixes to the learning to ship without a person in the loop | Repair policies: auto after replay, or after a canary |
| Your traces are worth training on | A model tuned on your decisions, trained and hosted for you |
| A second person's agents touch the same knowledge | Rooms, roles and attribution do not exist in the single-writer model |
| Someone new joins and their agent starts from nothing | Joining briefings hand it what the team already knows |
| Agents need to ask each other questions | Room discussions and structured negotiation |
| A wrong entry should be reviewed before it lands | Branching, pull requests, diff and merge |
| Somebody will ask why an agent did that, months later | Immutable traces, signed and queryable long after the session ended |
| You want one view of conflicts, stale knowledge and recurring failures across every agent | Pattern scans with triage and resolution tracking |
| Non-engineers need to see what agents know | Dashboard, expertise map, audit log |
| Learning must not leak secrets or PII | Security findings, custom policies, SIEM forwarding |
| You would rather not run Postgres, workers and upgrades | It is a hosted service |
